# Задача: расширение существующего скилла scenario-map для формирования трёх артефактов сценариев Core Agent

## 1. Контекст и цель

Необходимо доработать существующий локальный скилл `.gigacode/skills/scenario-map/`, используемый в GigaCode CLI.

**Это расширение существующего рабочего прототипа, а не создание нового скилла.**

### Бизнес-контекст

Core Agent выполняет задачи из Jira и SberTrack, используя LLM-агентов, Skills, MCP-инструменты, API и другие механизмы автоматизации.

Над развитием сценариев Core Agent работают разные команды и специалисты. Информация о сценариях распределена между паспортами, дорожными картами, схемами, презентациями и другой документацией.

Основные проблемы:
- Недостаточная прозрачность состояния и развития сценариев.
- Большое количество разрозненных артефактов.
- Ручное обновление нескольких документов при изменении процесса.
- Риск расхождений между документами.
- Сложность отслеживания зависимостей, блокеров и готовности к автоматизации.

### Целевая функциональность

Необходимо обеспечить централизованное создание и обновление трёх артефактов для каждого сценария Core Agent:

1. **Паспорт сценария** — цель, владелец, статус, триггер, DoD, зависимости, риски, сроки и другие характеристики.
2. **Дорожная карта** — этапы развития сценария, контрольные точки, сроки, статусы и блокеры.
3. **CJ-описание сценария** — структурированное описание прохождения сценария: участники, фазы, действия, точки взаимодействия, входные и выходные артефакты, развилки, проблемы и критерии успешности.

Все три артефакта должны формироваться из единой модели данных и быть доступны через HTML-визуализацию.

Основной принцип:

**Одно обращение к скиллу → сбор и согласование информации → обновление YAML → генерация согласованных артефактов → проверка результата.**

## 3. Универсальность решения

Скилл должен поддерживать разные сценарии Core Agent, например:
- Исправление минорного бага.
- Разработку новой функциональности.
- Code Review.
- Генерацию тест-кейсов.
- Формирование БТ и СТ.
- Генерацию автотестов.
- CI/CD.
- Другие сценарии, структура которых заранее неизвестна.

Не привязывай архитектуру к конкретному сценарию.

### Источники информации

Информация может поступать:
- Из интервью с пользователем.
- Из существующих YAML.
- Из презентаций PowerPoint.
- Из Markdown и другой доступной документации.
- Из предоставленных пользователем описаний процессов.

Наличие презентации или другого файла **не является обязательным условием работы скилла**.

Скилл должен поддерживать два варианта:

**Вариант A — создание с нуля.**

Если исходных документов нет, агент проводит интервью и формирует модель по подтверждённым ответам пользователя.

**Вариант B — создание или обновление на основе источников.**

Если пользователь предоставил документы, агент извлекает доступные сведения, сопоставляет их с существующей моделью и задаёт уточняющие вопросы только по отсутствующим или противоречивым данным.

При этом:
- Не выдумывать информацию.
- Не заменять TBD предполагаемыми значениями.
- Не считать исторические статусы автоматически актуальными.
- Не переносить общеплатформенные данные в паспорт конкретного сценария без оснований.
- При противоречиях запрашивать согласование.
- Не требовать обязательного подключения Jira, SberTrack или внешних сервисов.

Презентация «Статус по автономизации AI PDLC» может использоваться как тестовый источник, но не должна определять структуру решения.

## 4. Единая модель данных

Сохрани существующий принцип:

**YAML — канонический источник данных для генерации. HTML и другие представления являются производными артефактами.**

Переиспользуй существующие структуры:
- `passport`
- `roadmap`
- `steps`
- `edges`
- `integrations`
- `questions`
- `gaps`

Не создавай независимую модель шагов специально для CJ.

CJ должен формироваться на основе уже существующих шагов, переходов, паспортных данных и интеграций.

### Предлагаемое расширение YAML

Используй результаты предварительного анализа как основу.

Добавь необходимые необязательные поля в `passport`:

- `user_role` — роль пользователя или участника сценария.
- `journey_phases` — фазы прохождения сценария.
- `pain_points` — проблемы и затруднения.
- `success_metrics` — критерии и метрики успешности.
- `narrative` — связное описание прохождения сценария.

Для `steps[]` рассмотри:
- `touchpoint_type` — тип точки взаимодействия.

Поддерживаемые типы точек взаимодействия должны соответствовать реальным сценариям Core Agent. Не ограничивай их только классическими клиентскими каналами, если для технических сценариев требуются CLI, API, MCP, интерфейс трекера или иные типы.

Отдельно проверь необходимость явной привязки шагов к фазам CJ. Если массива `journey_phases` недостаточно, реализуй минимальный обратно совместимый механизм такой связи.

Не дублируй данные, уже содержащиеся в `steps`, `edges` или `integrations`.

Все новые поля должны быть необязательными.

Существующие YAML-файлы должны продолжать успешно обрабатываться без добавления новых полей.

### Важное уточнение по CJ

В данном проекте CJ — описание пути прохождения сценария Core Agent.

Не считай автоматически, что речь идёт только о классическом Customer Journey внешнего клиента.

Участниками могут быть разработчик, аналитик, тестировщик, оператор, AI-агент или другой участник процесса.

Сохраняй различие между:
- Ролью пользователя сценария.
- Исполнителем конкретного шага.
- Техническим инструментом выполнения.

Не заменяй одно понятие другим.

## 5. Доработка интервью

Измени `references/interview.md`.

Максимально переиспользуй существующие блоки интервью:
- Общая информация.
- Паспорт.
- Дорожная карта.
- Шаги.
- Развилки и петли.
- Межсценарные интеграции.
- Финальное согласование.

Добавь сбор CJ-данных в логически подходящие части интервью.

В частности, должны выясняться:
- Кто является пользователем или основным участником сценария?
- Какова цель прохождения сценария?
- С какого события начинается сценарий?
- На какие логические фазы он делится?
- Какие действия выполняются?
- Какие точки взаимодействия используются?
- Какие трудности и ручные операции возникают?
- Какие результаты ожидаются?
- По каким критериям оценивается успешность?
- Чем заканчивается сценарий?

### Требования к интервью

1. Не задавать повторно вопросы, ответы на которые уже существуют в YAML или подтверждены источником.
2. Не спрашивать обо всех необязательных CJ-полях при каждом небольшом обновлении.
3. Сохранять текущий принцип интервью блоками.
4. Не делать вывод о наличии инструмента или скилла только на основании его названия.
5. Фиксировать неизвестные сведения в `questions` или `gaps`, в зависимости от их смысла.
6. Не выдумывать сроки, статусы, роли и метрики.
7. Перед записью демонстрировать пользователю предлагаемые изменения.
8. Записывать изменения только после согласования.

В режиме `create` интервью должно позволять собрать информацию для всех трёх артефактов за один процесс.

В режиме `update` необходимо задавать только вопросы, относящиеся к изменяемой части сценария.

## 6. Генерация CJ

Расширь существующий генератор `scripts/mapgen.py`.

Реализуй отдельную функцию генерации CJ, например `build_cj_md()`, или эквивалентное решение, соответствующее текущей архитектуре.

Используй существующую обработку YAML и порядок шагов.

### Содержание CJ

Для каждого сценария CJ должен включать:

1. Название и назначение сценария.
2. Роль пользователя.
3. Триггер запуска.
4. Цель.
5. Ожидаемый результат.
6. Фазы прохождения.
7. Описание действий по шагам.
8. Участников и исполнителей.
9. Точки взаимодействия.
10. Входные и выходные артефакты.
11. Требования P/C/S/T.
12. Условия переходов.
13. Развилки и возвраты.
14. Связи с другими сценариями.
15. Болевые точки.
16. Метрики успешности.
17. Пользовательский нарратив, если он предоставлен.

### Требования к генерации

- Не выдумывать отсутствующие сведения.
- Не терять шаги.
- Не дублировать шаги из-за циклических переходов.
- Сохранять условия развилок.
- Корректно отображать возвраты.
- Сохранять реальные названия и идентификаторы.
- Не превращать все ветви графа в ложную линейную последовательность.
- Отмечать отсутствующие необязательные сведения как неизвестные или неуказанные.
- Не записывать текстовые заглушки в исходный YAML.
- Обеспечить детерминированность генерации.

Если CJ генерируется в Markdown, он должен создаваться автоматически из YAML, а не поддерживаться вручную.

Предусмотри CJ-файл для отдельного сценария и, если целесообразно, общий CJ-документ для всей карты.

## 7. Интеграция CJ в HTML

**Важно: конечная задача не ограничивается генерацией Markdown.**

CJ должен быть доступен пользователю в составе HTML-визуализации сценариев.

Максимально переиспользуй `assets/template.html`.

Предпочтительное решение — добавить CJ как отдельную вкладку или панель сценария рядом с существующими представлениями паспорта и дорожной карты.

Требования:
- CJ открывается для выбранного сценария.
- Его содержание соответствует YAML.
- Сохраняются существующие механизмы навигации.
- Не нарушается масштабирование SVG-карты.
- Не ломается паспорт.
- Не изменяется поведение диаграммы Ганта.
- Не нарушаются панели «Проблемы», «Свод» и реестр интеграций.
- Интерфейс остаётся читаемым при длинных описаниях.
- Для CJ не требуется ручная правка HTML.

Не внедряй новые элементы непосредственно в SVG-геометрию, если задачу можно решить отдельной панелью.

## 8. Обновление режимов работы

Сохрани существующие режимы:

### create

Создаёт новый сценарий через интервью, сохраняет YAML и формирует все поддерживаемые представления, включая CJ.

### update

Изменяет существующий сценарий:
- Читает актуальную YAML-модель.
- Определяет затронутые поля.
- Уточняет недостающие сведения.
- Показывает diff.
- Обновляет только согласованные данные.
- Перегенерирует связанные артефакты.

### rebuild

Перегенерирует все необходимые представления из существующего YAML без нового интервью.

Обнови инструкции `SKILL.md`, команды генерации и `README.md`.

При необходимости скорректируй `run-map.sh` и CI, сохранив обратную совместимость.

## 9. Валидация и ревью

Сохрани существующую систему проверки инвариантов и ревью двумя субагентами.

Расширь проверки для CJ.

Необходимо контролировать:
- Полноту переноса шагов.
- Соответствие CJ исходному YAML.
- Отсутствие дублирования шагов.
- Корректность ветвлений и возвратов.
- Соответствие интеграций реестру.
- Корректность пользовательских ролей.
- Сохранность входных и выходных артефактов.
- Корректное отображение отсутствующих данных.
- Согласованность трёх артефактов.

Ревью CJ должно проверять как содержание, так и читаемость HTML-представления.

Субагенты работают в режиме read-only. Исправления выполняет основной агент.
